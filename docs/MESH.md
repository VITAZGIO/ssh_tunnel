# Сеть устройств

Твои устройства — компьютер, ноутбук, телефон, домашний сервер — видят друг
друга по постоянным адресам и именам, как в NetBird или Tailscale. Только
посредник — не чужой облачный сервис, а твой собственный сервер, тот же, через
который идёт туннель.

```
  ноутбук.mesh  ──SSH──►  твой сервер (meshd)  ◄──SSH──  сервер.mesh (дома)
  198.19.0.1                                             198.19.0.2
```

Пример: дома стоит сервер с Docker, у контейнера порт 8080. С ноутбука в кафе
открываешь `http://domashniy-server.mesh:8080` — и попадаешь в этот контейнер.
Белый адрес дома, проброс портов на роутере и открытые наружу порты не нужны:
оба устройства и так ходят к серверу по SSH.

## Как включить

1. **На сервере** — служба `meshd`. Её ставит мастер настройки VPS (галочка
   «Заодно поставить сеть устройств») или панель на сервере: «Настройки» →
   «Сервер сети». Руками — см. ниже. Серверов может быть несколько — см.
   «Несколько серверов в одной сети».
2. **На первом устройстве**: Настройки → Настройки сервера → «Сеть
   устройств» → «Включить». Ключ сети создастся сам. Имя устройства — любое,
   из него получится имя `.mesh` (кириллица переводится в латиницу).
3. **На остальных**: либо «Экспорт» сервера с первого устройства (ключ сети
   едет вместе с ним, на телефон — QR-кодом), либо вставить тот же ключ руками.

## Кнопка на главном экране

Когда у сервера включена сеть устройств, под большой кнопкой появляется
маленькая — «Сеть устройств». Большая отвечает только за обход блокировок:
выключил её — сайты идут напрямую, а сеть устройств (и открытые RDP-сессии)
продолжает работать. Маленькая выключает и включает саму сеть. Подробнее —
в [VPN.md](VPN.md#обход-блокировок-и-сеть-устройств--по-отдельности).

## Доступ к компьютеру до входа в систему

На Windows VPN-версия с галочкой «Запускать при старте системы» ставится
службой и поднимает сеть устройств при включении компьютера, ещё до входа в
учётную запись. Включил компьютер удалённо — и подключаешься к нему по RDP с
экрана ввода пароля, как с NetBird. Нужны «Пускать другие устройства к моим
службам» на этом компьютере и включённый в Windows удалённый рабочий стол.
Подробнее — в [VPN.md](VPN.md#автозапуск-на-windows--служба).

## Что работает

- Имена `имя.mesh` и адреса `198.19.x.y` — в режиме прокси (браузер, curl,
  всё, что ходит через прокси) и в режиме VPN (Windows, Linux, Android — там
  любая программа).
- Адрес устройства постоянный: сервер запоминает его по id устройства.
- Входящие: «Пускать другие устройства к моим службам» — тогда
  `устройство.mesh:ПОРТ` ведёт на `127.0.0.1:ПОРТ` этого устройства. Выключи
  там, куда ходить не нужно (например, на телефоне).
- Сети разных людей на одном сервере разделены ключом: видят друг друга только
  устройства с одинаковым ключом. Сервер хранит не ключ, а его хеш.

## Несколько серверов в одной сети

Серверов может быть сколько угодно, и **главного среди них нет** (с meshd
версии 4). На каждом сервере работает свой `meshd`, а устройство держит
управляющее соединение с каждым сервером сети, который знает. Упал один
сервер — устройства уже на связи через остальные.

```
  ноутбук ──SSH──► Франкфурт (meshd) ◄──SSH── телефон
     └─────SSH───► Лондон    (meshd) ◄──SSH──────┘
```

- **Кто сервер сети.** На устройстве серверы сети — это профили с одним и тем
  же ключом сети и включённой сетью устройств. Профиль, к которому идёт
  туннель, — основной: с ним связь через пул туннеля. С остальными —
  лёгкое SSH-соединение только для сети устройств (интернет через него не
  идёт, локальных прокси нет). Вход — как в любой профиль: свой ключ и
  пользователь, ключ сервера проверяется по `known_hosts` программы. Поле
  профиля `meshOnlyThis` (в файле настроек) — «только этот сервер»:
  остальные не подключаются.
- **Кто может добавить сервер в сеть.** Тот, у кого на устройстве есть вход
  на этот сервер (его профиль) и ключ сети. Панель сервера может
  *советовать* устройствам другие серверы («Серверы сети» → «Советовать
  устройствам»): устройство показывает совет, но пойдёт туда, только когда на
  нём заведут профиль этого сервера — с той же проверкой ключа сервера, что
  и у профиля, добавленного руками. Сам совет входа не даёт.
- **Когда устройства видят друг друга.** Если у них есть хоть один общий
  сервер на связи. Соединение через сервер идёт через общий сервер, где
  второе устройство сейчас на связи; не вышло (сервер упал) — через
  следующий общий, за секунды. Прямые соединения (p2p, локальная сеть) от
  серверов не зависят и падения сервера не замечают.
- **Нет общего сервера.** Устройство, которое знает только Франкфурт, и
  устройство, которое знает только Лондон, друг друга не достанут. Если
  второе раньше было на общем сервере и рассказало, что оно теперь через
  Лондон, первое прямо скажет: «нет общего сервера с … : оно на связи через
  Лондон» — без 20-секундного ожидания.
- **Одно устройство — одна строка.** Устройство, подключённое к двум
  серверам, в списке одно (списки серверов сводятся по адресу), с пометкой,
  через какие серверы оно на связи. В панелях обоих серверов у него тот же
  адрес и то же имя.

### Адрес и имя устройства

Устройство само хранит свой адрес и имя (в `peers.json`) и называет их каждому
серверу, вместе с тем, с какого времени держит адрес. Серверы друг с другом
не говорят — спор решается одним правилом, одинаковым везде:

1. Адрес свободен на этом сервере — устройство его получает.
2. Адрес занят другим устройством — побеждает то, что держит его **дольше**
   (меньшее время «с какого момента»); при равенстве — меньший id
   устройства. Проигравший получает следующий свободный адрес из **своей**
   последовательности (хеш ключа сети, id устройства и номера), узнаёт его
   (`readdress`) и называет новый адрес остальным серверам.
3. Новое устройство без адреса начинает с той же последовательности —
   поэтому на разных серверах оно сразу получает один и тот же адрес.
4. Имя — так же: занято более старым устройством — проигравший получает
   имя с хвостом из своего id (`laptop-3f2a`), одинаковым на всех серверах.

Правило зависит только от двух устройств, поэтому любой сервер, который знает
обоих, решит одинаково. Старые устройства (до этой версии, без «с какого
времени») держат адрес с первого появления на сервере.

### Правила доступа, журнал и действия в панели

- **Правила доступа — свои у каждого сервера.** Панель показывает и меняет
  только правила своего сервера и говорит об этом. Устройства рассказывают
  каждому серверу, с какими ещё серверами они на связи и каков отпечаток их
  правил; если на другом сервере правила другие, панель пишет это крупно:
  устройство может пойти к другому через любой общий сервер, поэтому на деле
  действует самое мягкое из правил. Лекарство — одинаковые правила во всех
  панелях. (Копировать правила между серверами устройства не могут: права не
  должно задавать устройство.)
- **Журнал** — свой у каждого сервера: в нём только то, что видел этот
  `meshd`.
- **Переименовать** устройство в панели — имя получает и само устройство и
  несёт его на остальные серверы (побеждает переименование, сделанное
  позже). Старые версии программы имя не переносят: оно остаётся на том
  сервере, где его дали.
- **Убрать** устройство — убрать его запись **на этом сервере** и снять имя
  из панели. На других серверах оно остаётся, пока его не уберут и там; само
  устройство, если у него остался ключ сети, вернётся (с тем же адресом).
- **Удалить сеть** — на этом сервере. Другие серверы сеть хранят; на этот
  она вернётся, как только подключится устройство с тем же ключом.

### Батарея телефона

С одним сервером телефон за минуту обменивается с ним примерно так: 4 пинга
meshd (раз в 15 с) и ответы на них, 2,4 своих пинга (раз в 25 с) и 3
проверки SSH (раз в 20 с) — около 9,4 «пробуждений» в минуту. Дополнительный
сервер идёт «тихо»: meshd пингует его раз в 60 с (`quiet` в hello), своих
пингов устройство туда не шлёт, а SSH проверяется раз в 60 с — ещё около 2 в
минуту. Итого с двумя серверами ≈11,4, то есть ~1,2× от одного сервера
(предел — 1,5×). Мёртвый дополнительный сервер замечается за 2–3 минуты, но
соединения на это время не страдают: они идут через общий живой сервер.
На Android дополнительные серверы пока не подключаются (только сервер
туннеля, как раньше): общий код готов, не хватает списка серверов со
стороны приложения.

### Старый способ: побочный сервер

Работает как раньше и с новыми клиентами: на побочном сервере своего `meshd`
нет, его `127.0.0.1:47831` — SSH-проброс (служба `meshd-uplink`, пользователь
`meshlink`) к `meshd` другого сервера. Устройство с профилями обоих серверов
поймёт, что за ними один и тот же `meshd` (до hello оно спрашивает у сервера
`op id`; у старого `meshd` id нет — все старые считаются одним), и будет
держать одно соединение. В панели такой сервер помечен «старый способ».

Как подключить побочный сервер старым способом (нужна панель на обоих):

1. Панель сервера с `meshd` → «Сети» → «Серверы сети» → «Побочный сервер
   старым способом» → имя → «Получить код».
2. Панель побочного → «Настройки» → «Проброс к другому серверу» → вставить
   код → «Подключить».

Внутри кода — адрес и SSH-ключи сервера с `meshd` и отдельный ключ доступа
для побочного. Этот ключ принадлежит пользователю `meshlink`, которому
разрешено ровно одно — проброс до `127.0.0.1:47831`: ограничения стоят и в
`authorized_keys` (`restrict,port-forwarding,permitopen=…,command=nologin`), и
блоком `Match User meshlink` в `sshd_config`. «Отключить» убирает ключ и рвёт
соединение.

### Обновление: как перейти на серверы без главного

Пример — главный во Франкфурте, побочный (проброс) в Лондоне.

1. **Обновить программу на устройствах.** С прежними серверами всё работает
   как было: два пути к одному `meshd` (Франкфурт и проброс Лондона) клиент
   узнаёт и держит одно соединение. Старые устройства продолжают работать.
2. **Обновить `meshd` во Франкфурте** (панель → «Обновить meshd»). Адреса и
   имена устройств сохраняются, у сервера остаётся адрес `198.19.255.254`.
   Лондон по-прежнему проброс к нему — ничего не меняется.
3. **На каждом устройстве, которому нужна сеть, завести профили обоих
   серверов с одним ключом сети** (обычно они уже есть: Лондон — запасной).
   Устройства с одним лишь профилем Лондона после шага 4 будут видеть только
   тех, кто тоже на Лондоне.
4. **Перевести Лондон на свой `meshd`**: панель Лондона → «Настройки» →
   «Перейти на свою службу сети» → «Установить службу сети». Проброс
   снимается, ставится `meshd`, прежний адрес Лондона в сети (например
   `198.19.255.253`) переходит в его `meshd`. Устройства с двумя профилями
   сами начнут держать связь с обоими; адреса у них остаются прежними
   (устройство называет свой адрес, Лондон его принимает). В панели Франкфурта
   Лондон останется в «старом способе» без связи — «Отключить» убирает его
   ключ `meshlink`.
5. **Задать одинаковые правила доступа** в обеих панелях — пока они разные,
   панели об этом пишут.

Старые программы на устройствах (без этой версии) после шага 4 ходят только
к серверу своего профиля и при переходе на запасной могут получить там
другой адрес — их стоит обновить.

## Профиль устройства в панели

Панель сервера не только называет устройство и задаёт правила, но и
управляет им (ТЗ 16, `meshd` версии 5): одобряет новые устройства,
замораживает их и советует цепочку выхода. Панель — подсказка, а не замок:
человек на устройстве может поменять то, что она задала.

### Одобрение новых устройств

«Сети» → у сети галочка «Новые устройства — после одобрения» (по умолчанию
выключена — как раньше). Устройство, которого в сети ещё не было, после
этого приходит **ждущим**: оно на связи с сервером и видно в «Устройствах»
со значком «ждёт одобрения», но в списке у него только оно само, его нет в
списках других, и ни оно никуда, ни к нему никто не подключится — ни через
сервер, ни напрямую. В журнале — «… ждёт одобрения». «Одобрить» — пустить,
«Отклонить» — убрать (как «Убрать»: подключится снова — снова будет ждать).
Выключение галочки ждущих не одобряет: их решают руками.

Ждущее устройство не отнимает у одобренного ни адрес, ни имя (в споре за
адрес оно всегда проигрывает), иначе любой с ключом сети мог бы выбивать
чужие адреса заранее.

### Заморозка

«Заморозить в сети» в карточке устройства: адрес и имя остаются, оно
остаётся в списке панели и на связи с сервером, но пока его не разморозят,
оно никуда не подключается и к нему никто. Идущие через сервер соединения
рвутся сразу. Прямые (p2p) — тоже: замороженное пропадает из списка
устройств у остальных, а клиент держит прямые соединения только с
устройствами из списка и закрывает их, как только устройство из него
пропало (так же работает «Убрать»). Само замороженное получает список только
из себя и закрывает свои. Это не то же самое, что заморозка клиента SSH
(«Вход на этот сервер» → «Заморозить»): та не пускает на сервер вовсе.

### Несколько серверов и без сервера

- **Одобрение и заморозка — у каждого сервера свои**, как правила доступа:
  права не приезжают с устройств. Одобрили на одном сервере и не на другом —
  через второй устройство никого не видит; заморозили на одном — через
  другой общий сервер оно по-прежнему ходит (действует самое разрешающее).
  Чтобы закрыть устройство совсем, заморозь его во всех панелях. Само
  устройство видит, на каком сервере оно ждёт или заморожено.
- **Без сервера правила не проверяет никто.** Устройство, которое было вне
  связи, пока другое заморозили, ещё помнит его и пустит напрямую в одной
  локальной сети — до своей следующей связи с сервером. Новое ждущее
  устройство без сервера не найдёт никого: знакомство всегда через сервер.

### Цепочка выхода из панели

В карточке устройства — «Выход в интернет (цепочка)»: вход (сервер, через
который устройство подключается) и до двух серверов после него, из тех, для
которых у устройства есть профиль (устройство само рассказывает о своих
профилях: `op profiles`). «Отправить на устройство» — и оно ставит эту
цепочку в «Выход через» профиля входа так, как если бы человек выставил её
сам; если это активный сервер, туннель переподключается.

- **Ключ сервера — «адрес:порт» SSH** (адрес маленькими буквами, порт по
  умолчанию 22). Id профилей у каждого устройства свои, а id `meshd` есть
  только у серверов с сетью устройств — звеном же выхода бывает любой
  SSH-сервер. Те же адрес и порт несёт цепочка в файле обмена (ТЗ 8). Два
  профиля одного сервера под разными пользователями — берётся первый.
- **Новее — побеждает**, как с именем из панели: у цепочки профиля есть
  время и источник (`exitT`, `exitBy`). Устройство применяет цепочку из
  панели, только если она новее своей, и рассказывает всем своим серверам,
  что вышло, — панель показывает значение устройства, «задано в панели
  сервера X» или «задано на самом устройстве» и предупреждение, если на
  устройстве поменяли после панели. Время берётся не меньше прошлого+1 и в
  панели, и на устройстве, поэтому правка, сделанная после чужой, побеждает
  её даже при сбитых часах. Две панели — побеждает та, что задала позже.
  `meshd` повторяет свою цепочку при каждом подключении устройства, пока оно
  не применит её (или более новую).
- **Звена нет на устройстве** — цепочка всё равно ставится, а туннель не
  стартует и говорит «нужен профиль сервера …»: молча выйти в интернет не
  там нельзя. Появится профиль с этим адресом — звено станет им само.
- Окно устройства показывает, откуда цепочка («задано в панели сервера X,
  время»), а серверы, которые советуют панели, — с кнопкой «Добавить
  профиль»: новый профиль открывается с адресом и ключом сети, вход и ключ
  вписывает человек, ключ сервера проверяется как всегда.
- Панель видит список всех профилей устройства (адрес, порт, имя), а не
  только серверов этой сети.

## Панель на сервере

- Плитки: сколько устройств и серверов в сети, средняя задержка, трафик
  между устройствами.
- Схема сети: этот сервер в центре, старые побочные вокруг, у каждого — его
  устройства; цвет и бегущие линии — живая связь и её качество.
- Карточка устройства: адрес и имя `.mesh`, система и версия программы,
  режим (прокси или VPN), через какой сервер подключено, задержка (RTT),
  джиттер, потери, трафик, сколько раз подключалось.
- Переименование прямо в карточке: новое имя `.mesh` сразу видят все
  устройства этого сервера и само переименованное, а оно несёт его дальше.
  «Убрать» освобождает адрес на этом сервере.
- Одобрение, заморозка и цепочка выхода — там же (см. «Профиль устройства в
  панели»).
- «Серверы сети»: этот сервер, другие серверы сети по рассказам устройств
  (с пометкой «правила те же / другие»), старые побочные и список серверов,
  которые панель советует устройствам.

Задержку меряет сам `meshd`: раз в 15 секунд шлёт каждому устройству (и
каждому старому побочному серверу) ping с меткой времени; дополнительному
соединению устройства — раз в 60 секунд.

## Ограничения

- Только TCP (веб, SSH, базы, RDP по TCP…). UDP между устройствами пока нет.
- Устройства по возможности соединяются **напрямую** (QUIC по UDP, пробивание
  NAT, в одной локальной сети — по локальным адресам); не вышло — через сервер,
  и тогда скорость не выше, чем у двух туннелей до него. Сервер нужен, чтобы
  свести устройства в первый раз: напрямую без него можно только с теми, с кем
  прямой путь уже был.
- Службе на устройстве надо слушать `127.0.0.1` или `0.0.0.0` (Docker с
  опубликованным портом — как раз так).
- Без сервера правила доступа (`policy` в панели) никто не проверяет. Прямой
  путь meshd сводит только между устройствами, которым правила разрешают всё
  в обе стороны, а без сервера пускаются лишь устройства из последнего списка
  с запомненным отпечатком ключа. Но если правила ужесточили, пока устройство
  было не в сети, оно узнает об этом только при следующей связи с сервером.
  Так же с заморозкой: пропустившее её устройство пустит замороженное
  напрямую до своей следующей связи с сервером.

## Без сервера

Домашний интернет пропал — устройства, которые видят друг друга напрямую, не
теряют связи: общий буфер, зеркальные папки, файлы.

- **Прямые соединения живут дольше управляющего.** Обрыв связи с `meshd` их не
  закрывает, переподключение — тоже. Состояние сети — `local`: «без сервера,
  напрямую: N», устройства с прямым путём — на связи.
- **Постоянный ключ.** Ключ ed25519 прямых соединений создаётся один раз и
  хранится рядом с настройками (`<StateDir>/<id сети>/key`, права 0600; на ПК —
  папка настроек программы, на Android — личная папка приложения). Отпечаток
  после перезапуска тот же, поэтому соседи узнают устройство и без сервера.
- **Список на диске** (`peers.json` там же): адреса, имена, отпечатки,
  последние рабочие адреса прямого пути, когда было на связи. Имена `.mesh`
  отвечают и без сервера.
- **Поиск в локальной сети.** Без сервера, пока к кому-то из списка нет
  прямого пути, устройство шлёт маяк: широковещательно на UDP 47839 и адресно
  на последние рабочие адреса. Маяк подписан HMAC-SHA256 ключом сети, в нём id
  сети (хэш ключа, не сам ключ), адрес, порт, отпечаток и время; чужой,
  устаревший (окно 2 мин) или повторённый не принимается. Дальше — обычное
  рукопожатие QUIC с проверкой отпечатка. Частота: при живом сервере маяков
  нет; без сервера — сразу, через 2 и 4 с, потом раз в ~30 с.
- **Нет прямого пути и нет сервера** — соединение сразу получает понятный
  отказ, без 20-секундного ожидания.
- **Старт без сервера** (с версии ТЗ 6). Клиент сети живёт по кнопке «Сеть
  устройств», а не по SSH-соединению: программа запустилась (или ПК
  перезагрузился), а сервер не отвечает — клиент всё равно поднимается из
  кэша на диске и ищет соседей. Круглая кнопка гаснет с обычной ошибкой
  сервера (обхода без сервера нет), «Сеть устройств» остаётся включённой, а
  туннель поднимается «местным»: локальные прокси или адаптер VPN с режимом
  «только сеть устройств», сервер ищется в фоне. Появился сервер — клиент
  входит к нему сам, без перезапуска; круглую кнопку включает человек (или
  автозапуск, который повторяет попытки). То же, если сервер пропал насовсем
  и не поднялся запасной: гаснет только обход.
- **Что видно.** Строка состояния сети: «Без сервера, напрямую: N», когда
  кто-то на прямой связи, и «Нет связи, соседей не видно», когда нет ни
  сервера, ни соседей. `ssh_tunnel state` печатает то же (строка
  «Устройства:»), `--json` — поля `meshLink` и `meshDirect` в `GET /api/state`.
- **Режимы.** В режиме VPN имена `.mesh` и адреса `198.19.x.y` идут через
  адаптер в сеть устройств, как обычно. В режиме прокси системный прокси в
  режиме «только сеть» не ставится (как и с сервером): `.mesh` доступны
  программам, которые ходят через SOCKS/HTTP-прокси программы, и плагинам
  (общий буфер, файлы, SSH) — они ходят в сеть устройств сами.
- **Android** (с ТЗ 11) — так же, как ПК. Клиент сети держит
  `mobile.Tunnel` (свой `tunnel.MeshHost`), пул SSH только даёт ему путь к
  серверу. Первое подключение не удалось, а «Сеть устройств» включена —
  `StartCore` поднимает туннель ещё раз с `ServerOptional`: служба VPN не
  останавливается, интерфейс поднимается (только IPv4 — спросить про IPv6
  некого), обход выключен с ошибкой сервера (`ServerDownText`/`Kind`, на
  экране — ошибкой на круглой кнопке, как `core.ServerDownError`). Включить
  обход, пока сервер так и не ответил, нельзя: `SetModes` вернёт ошибку и
  подтолкнёт пул. Сервер ищется тем же пулом, что после обрыва: пауза 1 с,
  удваивается до ~30 с (с разбросом), сбрасывается на 1 с при смене сети и
  при включении экрана (только пока связи нет). Появился сервер — тот же
  клиент входит к нему.
  - **Wi-Fi.** Сокет прямых соединений и маяков привязан к Wi-Fi
    (`Callbacks.BindLAN` → `Network.bindSocket`): дома без интернета Android
    уводит основную сеть на мобильную, и без привязки маяки ушли бы туда.
    Wi-Fi появился, пропал или сменился — клиент пересоздаётся
    (`LANChanged`: прежний останавливается, новый с тем же ключом и кэшем).
    Без Wi-Fi сокет не привязан и идёт основной сетью, как раньше.
  - **MulticastLock** берётся, только пока он нужен: сервера сети нет, кого-то
    из знакомых устройств не видно напрямую (`MeshSummary().beacons`) и
    телефон в Wi-Fi; иначе отпускается. Без него при выключенном экране
    Android отбрасывает широковещательные пакеты — чужие маяки не доходят
    (адресные маяки и свои — доходят и так). Цена — приём всего
    широковещания сети, пока экран выключен; поэтому только на время поиска.
  - **Что видно.** Уведомление при выключенном обходе: «Сеть устройств: в
    сети, через сервер» / «Без сервера, напрямую: N» / «Нет связи, соседей не
    видно» (ru/en); `/api/state` телефона отдаёт `meshLink`/`meshDirect`, как
    ПК.

Что происходит в особых случаях:

- **«Убрать» устройство в панели.** Те, кто на связи с сервером, получают
  новый список: убранное выпадает из него, прямые соединения с ним
  закрываются, без сервера оно больше не пускается. Кто в этот момент был не в
  сети, узнает при следующем подключении к серверу; до тех пор, если сервер
  так и недоступен, он ещё может соединиться с убранным напрямую (ключ сети у
  того остался).
- **Смена ключа сети.** Устройства с новым ключом — это новая сеть: новая
  папка состояния, новый ключ устройства, пустой список; маяки старой сети не
  проходят проверку подписи. Устройства со старым ключом, оставшиеся без
  сервера, продолжают видеть только друг друга, пока им не перенесут новый
  ключ.
- **Старые версии программы** (ключ на каждый запуск) работают как раньше:
  через сервер и напрямую при живом сервере; без сервера — только уже
  открытые прямые соединения.

## Как устроено

`meshd` (`src/cmd/meshd`) слушает только `127.0.0.1:47831` на сервере — до
него дотягиваются лишь через SSH-туннель. Каждое устройство держит к нему
управляющее соединение (к каждому серверу сети — своё): называет свой адрес,
получает список устройств и вызовы. Протокол и его необязательные поля для
нескольких серверов описаны в начале `src/cmd/meshd/main.go`. Когда
ноутбук открывает `сервер.mesh:8080`, он просит `meshd` соединить; `meshd`
зовёт домашний сервер по его управляющему соединению, тот открывает встречное
соединение, и `meshd` сшивает два потока. Клиентская сторона —
`src/internal/mesh`; в ядре туннеля такие цели идут в сеть устройств раньше
всех правил.

Прямые соединения (`src/internal/mesh/p2p.go`) — свой UDP-сокет мимо
туннеля; `meshd` передаёт между устройствами предложения (адреса и отпечаток
ключа) и отвечает на STUN. Маяки и хранение — `beacon.go`, `store.go`.

`meshd` — один файл на стандартной библиотеке Go: мастер скачивает готовую
сборку со страницы релиза, а если её нет — собирает прямо на сервере.

### Плагины на сервере и «кто звонит» (op who)

Сервер сам может быть участником сети: хост плагинов `ssh_tunnel_node`
слушает `127.0.0.1:47835–47838` (файлы, зеркальные папки, общий буфер,
резервные копии). Устройство звонит на `198.19.255.254:ПОРТ`, `meshd`
проверяет «Сервер в сети устройств» и права доступа (как для любого порта
сервера) и открывает соединение с `127.0.0.1:ПОРТ`, запоминая его исходный
порт. Хост на каждое соединение спрашивает `meshd`
`{"op":"who","port":N,"src":M}` и получает сеть, устройство, имя и
SSH-пользователя. `meshd` отвечает только про соединения, которые открыл сам
и которые ещё живы, и только процессу, который слушает этот порт (uid из
`/proc/net/tcp`), — подделать «кто пришёл» нельзя ни с другой машины, ни
другим пользователем сервера. Старый `meshd` на `who` не отвечает — плагины
тогда никого не пускают. На побочном сервере `meshd` — пересылка, опознание
там не работает: плагины ставят на главный. Проверка всего пути с настоящим
`meshd` — `src/internal/node/e2e_test.go`.

### Постоянный id устройства для служб (ТЗ 18)

Адрес и имя устройства в сети могут смениться (ТЗ 12), поэтому права служб
(зеркальные папки) держатся на постоянном id. Это не сам id устройства — он
служит устройству паролем в `dial`/`accept`, — а
`sha256("ssh_tunnel peer v1\0" + id)`, первые 12 байт в hex (`peerID` в
`meshd`, `mesh.PeerID`, `nodeapi.PeerID` — тест сверяет образец). Новый `meshd`
шлёт его необязательным полем `id` в списке устройств (`peers[].id`, у
серверов — от id сервера) и `fromId` во `incoming`. Служба устройства получает
его в `mesh.Caller.ID`: через сервер — из `fromId`, а если сервер старый — из
общего списка по адресу (его мог прислать другой, новый сервер); по прямому
соединению и без сервера (`local`) — из списка по адресу, который проверен
отпечатком ключа. Не узнать — пусто, и служба такому не даёт ничего нового.
Старые устройства новые поля не читают. Устройство, «убранное» в панели и
пришедшее с новым id, — новое устройство.

## Установка руками

```bash
# на сервере под root; для arm64 — meshd_arm64
curl -fsSL -o /usr/local/bin/meshd \
  https://github.com/VITAZGIO/ssh_tunnel/releases/latest/download/meshd
chmod +x /usr/local/bin/meshd
cat > /etc/systemd/system/meshd.service <<'UNIT'
[Unit]
Description=ssh_tunnel - сеть устройств (только 127.0.0.1)
After=network.target

[Service]
ExecStart=/usr/local/bin/meshd -state /var/lib/meshd/state.json -admin /run/meshd/admin.sock
Restart=always
DynamicUser=yes
StateDirectory=meshd
RuntimeDirectory=meshd
NoNewPrivileges=yes
ProtectSystem=strict
ProtectHome=yes

[Install]
WantedBy=multi-user.target
UNIT
systemctl daemon-reload && systemctl enable --now meshd
```

Если пользователю туннеля закрыт доступ к самому серверу (шаг 3 в
[SERVER_SETUP.md](SERVER_SETUP.md)), в правилах нужно исключение для
`127.0.0.1:47830-47831` — в свежей версии скрипта оно уже есть.
