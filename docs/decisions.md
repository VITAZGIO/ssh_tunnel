## 2026-11-03 — Android на общем HTML (ТЗ 2, второй шаг)

- **Главный экран телефона — тот же `index.html`, что окно ПК**, в WebView
  (`MainActivity`). Родные экраны (главный, настройки, серверы, приложения,
  реклама, домены, сеть устройств, пользователи) удалены. Нативными остались
  VPN-служба, плитка и мост `SSHTunnelAndroid` — то, что умеет только
  телефон: системный вопрос о VPN, камера для QR, буфер, файлы, внешние ссылки,
  кнопка «Назад».
- **API на телефоне — те же адреса и JSON, что `webui`**: `uihost` отдаёт
  Книгу и приложения сам, остальное `/api/` — обработчику платформы
  (`mobile.SetAPI` → `AndroidApi.kt`), поток `/events` общий (`mobile.Emit`).
  Настройки остаются в `Settings` (SharedPreferences): перенос в `config.json`
  ядра сейчас — риск потерять настройки при обновлении без проверки на
  телефоне; сделать вместе с переносом состояния кнопок в `core.Machine`.
  `core.State` на телефоне пока собирается из состояния службы.
- **Отличия телефона — в одном HTML**: класс `android` у `body` (мост есть) и
  метки `desk-only` / `android-only`. Ключ сервера — «Вставить ключ»
  (`/api/key`) вместо пути к файлу; приложения — по пакетам со значками;
  мастер — только «Пользователь»; нет тонкой настройки соединения, портов
  прокси, автозапуска системы, точки доступа.
- **Стрелка быстрого доступа на телефоне — та же, что на ПК** (только на
  главном экране, правило в `index.html`); родная стрелка, которая была видна
  на всех экранах, ушла вместе с родным экраном.
- Шаги в одном PR отдельными коммитами, каждый собирается и VPN работает:
  мост в ядре → API на Kotlin и режим телефона в HTML → WebView вместо
  родного экрана → удаление дублей.

## 2026-11-02 — QR и ссылка при создании клиента в панели (п. 16)

- QR и «Скопировать ссылку» — **только при создании** клиента: сервер отдаёт
  их лишь в ответе `/api/clients/create`, `/api/clients/config`
  («Показать настройки») — без них. Показывать для любого типа устройства.
- QR несёт ссылку `sshtunnel://import?v=1&d=…` (`docs/IMPORT_LINK.md`), а не
  JSON: короче (код реже), и камера телефона сразу открывает приложение.
  В ссылке только вход (адрес, порт, пользователь, ключ) и привязка к панели.
- Ссылку читает `share.Parse` — значит, её сразу понимают сканер и буфер на
  Android и «Вставить» на ПК, без второго разборщика. Старые версии
  приложения QR из новой панели не прочитают — нужно обновиться.

## 2026-11-02 — ядро 2.0, этап 1 (релиз v1.9.0)

- **Ядро — `src/internal/core`, одно на все платформы.** Две кнопки
  (`Machine`), одно место применения (`Driver.Apply`), одно решение «куда»
  (`Decide`). Причина: функции писались по 2–3 раза (окно ПК, Android,
  настройки), режимы расползались, после переключений оставалось старое
  состояние, которое лечилось перезагрузкой.
- **Кнопки независимы.** Круглая — только туннель, «Сеть устройств» — только
  своя связь. Четыре режима — сочетания. Нажатие во время «Подключаюсь…» —
  отмена этого подключения. Прежнее «Подключить» включало и сеть устройств,
  «Отключить» гасило обе — больше так нельзя; «Выключено» — `POST /api/state
  {"tunnel":false,"mesh":false}` или `/api/stop`.
- **Режим применяется целиком.** `Apply(режим, гигиена)` получает полный план
  (`core.PlanVPN`): маршруты, DNS, запрет DNS мимо адаптера, маршруты к
  серверу. Повторный `Apply` с тем же режимом — после смены сети, пробуждения,
  смены правил — ставит всё заново.
- **Гигиена переключения** (`core.Transition`): при смене круглой кнопки —
  сброс таблицы fake-IP и DNS-кэша системы, закрытие соединений из адаптера;
  при выключении сети устройств — закрытие её соединений; всегда — пересчёт
  решения для каждого живого соединения и закрытие тех, у которых оно
  изменилось. Так ушла поломка «после выключения обхода сайты продолжают идти
  через сервер» (браузер держал соединения HTTP/2).
- **Устаревший подставной адрес — сразу отказ (RST)**, а не попытка
  соединиться: приложение спрашивает имя заново.
- **Прямые соединения на Windows** — к привязке сокета (`IP_UNICAST_IF`)
  добавлен маршрут к адресу через роутер настоящей сети на время соединения
  (`PinDirect`, как давно сделано для сервера). Причина: с включённой точкой
  доступа и другими фильтрами Windows сверяет ответы с таблицей маршрутов —
  соединения «напрямую» висели в SYN_SENT (ноутбук, 02.11). Маршруты не
  ставятся к локальным сетям и 100.64/10; потолок 2048, живут 2 минуты после
  последнего соединения, при смене сети переставляются.
- **Linux: маршрутов к прямым адресам не ставим**, остаётся `SO_BINDTODEVICE`.
  При строгом `rp_filter=1` (RHEL/Fedora) ответы на прямые соединения может
  отбрасывать ядро — проверить на живой системе, при необходимости сделать
  маршруты, как на Windows.
- **Исключённые программы (NetBird) и fake-IP.** DNS в Windows спрашивает
  системная служба, программу по DNS не узнать. Поэтому исключённая программа
  может прийти на подставной адрес — стек возвращает имя, ядро решает
  «напрямую», прямое соединение разрешает имя через DNS настоящей сети. Для
  UDP то же самое (`tunnel.RouteUDP`, раньше UDP шёл только через
  ретранслятор или отбрасывался) — нужен NetBird/WireGuard.
- **Поток событий — SSE (`/events`), а не WebSocket.** Односторонний поток,
  работает в WebView2, Android WebView и браузере без библиотек; команды идут
  POST-ами. Набросок ТЗ допускал уточнение.
- **API полный и с самоописанием** (`GET /api`), ключ в заголовке
  `Authorization: Bearer`, адрес и ключ — в `api.json` в папке настроек: на
  нём строятся PowerShell, MCP, сторонние программы (просьба владельца).
- **Карта архитектуры — `docs/ARCHITECTURE.md`**, а не `docs/architecture.md`
  из ТЗ: на Windows имена файлов без учёта регистра, два файла столкнулись бы.
- **Android в этом этапе:** ядро Go на телефоне уже общее (решение «куда»,
  DNS, гигиена переключения, UDP напрямую), служба при выключении одной
  кнопки не останавливается. Не сделано: общий HTML-интерфейс в WebView и
  перенос состояния кнопок из Kotlin в ядро — следующий шаг этапа: без
  проверки на телефоне выкатывать новый интерфейс автообновлением опасно.

## 2026-11-02 — ТЗ 2: плагины, Книга, отдельные окна

- **Android на общий HTML — в два шага (решил владелец).** Этот PR: общие
  страницы `apps.html` и `book.html` (`src/internal/uiassets`) с мостом
  `SSHTunnelAndroid` (WebView, `WebPageActivity`) — их отдаёт ядро на телефоне
  (`internal/uihost` через `mobile.StartUI`) с тем же API, что на ПК. Новые
  разделы появляются на телефоне без кода под Android. Главный экран и
  настройки на телефоне пока свои: перевод всего API (настройки, серверы,
  выбор приложений, QR, разрешение VPN) — следующим PR, его можно проверить
  только на телефоне.
- **Страницы — в `internal/uiassets`, а не в `webui/assets`:** их встраивает и
  окно ПК (`webui`), и телефон (`uihost`), а `webui` тянет настольную часть.
  Цвета и темы вынесены из `index.html` в `theme.css` — одни на все страницы.
- **Плагины — `internal/addons`.** Описание (манифест) одно
  на все платформы, каталог — в коде (`manifest.go`). Список добавленного,
  звёздочки, выключатели, «подсказку видел» — у ядра в `addons.json` в папке
  настроек (своё на каждом устройстве). Модуль ядра приложения
  (`addons.Register`) работает только у активного приложения: добавлено,
  доступно на этом устройстве, фоновое — включено; страница
  `/addons/<id>.html` у неактивного — 404. Образец (`sample`) — только в
  сборке `dev`, в релизе его нет.
- **Иконки — Material Symbols (Apache 2.0), файлы внутри программы**
  (`uiassets/icons`), рисуются маской цветом текста. На Android стрелка
  быстрого доступа — тот же значок векторной картинкой.
- **Книга — Markdown в `docs/book/`, копия для сборки — в
  `src/internal/book/text/`** (`go generate ./internal/book`; тест сверяет).
  `go:embed` не достаёт файлы вне модуля, а Книга должна работать без
  интернета; так же сделано с `udprelay_server.go.txt`. Разметку разбирает
  страница (простой Markdown без библиотек). На ПК листается страницами
  (колонки CSS высотой в страницу, в широком окне — разворот), на телефоне —
  прокрутка.
- **Отдельные окна на Windows — каждое на своём потоке со своим циклом
  сообщений** (`nativeui.OpenWindow`): так они не зависят от главного (оно
  прячется в трей) и закрываются своим крестиком. Место и размер — в
  `windows.json` у окна (не в `addons.json`: в VPN-версии окна открывает
  процесс окна, а список приложений хранит служба). Окно с тем же ключом
  второй раз не открывается — показывается открытое. При неудаче отдельного
  окна старые процессы WebView2 не закрываются (это процессы главного окна).
  В браузере (Linux `-web`) — `window.open`, место помнит браузер
  (`localStorage`): нативного окна у Linux-версии нет.
- **Страницы интерфейса открыты без ключа** (и в `webui`, и в прокси окна
  VPN-версии): это код, а не данные; данные — только через `/api`, `/events`
  и `/addons/` с ключом. Иначе стили и значки (`theme.css`, `icons/*.svg`) не
  грузились бы — браузер не передаёт ключ в адресах стилей.
- **Linux: маршруты к прямым адресам и к серверу через роутер настоящей сети**
  (`vpnlayer/pins_linux.go`), как на Windows (запись выше от 2026-11-02 про
  Linux). Выбран маршрут /32, а не fwmark + `ip rule`: при строгом
  `rp_filter=1` ядро проверяет обратный путь без метки (пока
  `src_valid_mark=0`), и fwmark сам по себе ответы не спасает; маршрут к
  адресу честен и для отправки, и для проверки. У маршрутов метка `proto 94`
  — по ней после аварийного выхода оставшиеся снимаются при запуске. На
  Fedora руками ещё не проверено (CHECKLIST, п. 17).

## 2026-11-03 — ТЗ 3: диагностика

- **Четыре приложения — «Проверить сайт», «Кто трогает трафик», «Проверка
  утечек», «Отчёт для поддержки»** (`internal/diag`, каталог —
  `addons/catalog_diag.go` отдельным файлом, чтобы параллельные ТЗ не
  правили одну строку каталога). API — `/api/diag/…`, отвечает только у
  добавленного и включённого приложения.
- **Пока только Windows и Linux**: на Android приложения серые с причиной.
  Нужны проверки на стороне службы VPN (другой VPN, «Частный DNS»,
  батарея), а перевод телефона на общий интерфейс — отдельный PR (решение
  ТЗ 2).
- **Путь «через VPN» — `tun.Dial` (имя разрешает сервер) и DNS через DoH
  Cloudflare по туннелю; «напрямую» — тот же диалер и DNS настоящей сети,
  что у правила «напрямую»** (`Tunnel.DialDirect`). Подмена DNS — адрес-
  заглушка (0.0.0.0, локальные) или чужой сертификат при других адресах, чем
  через VPN. Заглушка в HTTP — по 451, перенаправлению и словам на маленькой
  странице. Фразы итогов — в одном месте (`diag/verdicts.go`).
- **Кнопка правила и «Исправить» в утечках — обычный `POST /api/config`**, тот
  же, что у экрана настроек, без отдельного пути.
- **«Кто трогает»: остановка только по `…/try`** (кнопка «Разрешаю»).
  Службы и обходы DPI на Windows останавливаются через `sc`/`taskkill`, без
  прав — с окном UAC. «Отключить насовсем» — тип запуска службы «вручную» или
  удаление записи из Run (запоминается, «Вернуть» ставит обратно); с диска
  ничего не удаляется. «Помирить» — только где у программы есть список
  исключений (zapret: `--ipset-exclude`/`--hostlist-exclude`). Linux — через
  systemd, нужен root. Адаптер NetBird (`wt0`) считается NetBird, а не
  WireGuard.
- **Утечки: «что видят сайты» — клиентом, который ходит как браузер**
  (системный прокси в режиме прокси, напрямую в режиме VPN); адрес — своя
  точка `/ip` на панели сервера, запасная — ipify; страна/провайдер и DNS —
  ip-api.com (уникальное имя `*.edns.ip-api.com`). Утечка DNS — резолвер в
  той же AS, что провайдер. Молчаливая проверка — модуль ядра у включённого
  приложения, сообщение в журнал только при утечке.
- **Журнал на диске** (`journal.log`, два файла по 1 МБ: записи журнала,
  смены состояния, неудачные соединения) пишется всегда — иначе в отчёте не
  было бы «последних дней». Удачные соединения не пишутся.
- **Маскирование в отчёте — по именам полей и по виду значения** (PEM, ключи
  ssh, длинные строки из букв и цифр), плюс найденные значения и ключ из
  `api.json` вычищаются из всех текстов. Пароль, вписанный обычными словами в
  свободный текст, так не поймать — в журнал программа пароли не пишет.
- **«Поделиться» на Windows — файл в буфер обмена** (вставляется в мессенджер
  как вложение) и Проводник с выделенным файлом: системное окно «Поделиться»
  Windows доступно только через WinRT. Linux — папка с файлом.

## 2026-11-03 — ТЗ 7: календари вместо DAVx5

- **CalDAV/CardDAV — свой клиент на net/http (`internal/calendar`), а не
  `emersion/go-webdav`.** Нужна малая часть протокола (поиск календарей,
  `sync-collection` по sync-token, `multiget`, PUT/DELETE с ETag), а
  настольная версия держится на трёх зависимостях. iCalendar разбирается
  сам: правка меняет только свои строки события (название, время, место,
  описание), напоминания, участники, повторы и поля Nextcloud остаются как
  были. Сервер не помнит токен — полная сверка по ETag.
- **Конфликты решает сервер:** запись с `If-Match`, 412 → сразу перечитать,
  показать версию сервера и пометку `conflict`. Своего слияния нет.
- **Путь до Nextcloud выбирает ядро.** Календарь ходит не системным
  прокси, а через `Tunnel.DialSelf` → `core.Decide` (имя `.mesh` — в сеть
  устройств, домашний адрес — напрямую): решение «куда» по-прежнему в одном
  месте. Туннель выключен — напрямую (тогда `.mesh` недоступен, о чём
  говорит ошибка). На Android приложение исключено из своего VPN, поэтому
  `.mesh` идёт тем же `DialSelf`, а не через адаптер.
- **Пароль приложения:** Windows — DPAPI (`calendar.key`), Linux и Android —
  файл 600 в личной папке программы. Общее хранилище секретов (Keystore,
  связка ключей Linux) делает ТЗ 4 — календарь переедет на него, когда оно
  появится, чтобы не было двух разных.
- **Свои адреса API у приложения — `addons.RegisterRoutes`:** таблица
  маршрутов общая, но отвечают они только у активного приложения (как
  страница). Календарь — первое приложение со своим API.
- **Android: системный календарь только для чтения.** Kotlin переносит
  готовое из ядра (`mobile.CalendarExportJSON`) в CalendarContract —
  повторы правилом RRULE, их разворачивает система; изменённые повторы —
  через `ORIGINAL_SYNC_ID`. Правка — в самом приложении: она сразу уходит на
  сервер, и не нужна вторая логика выгрузки «грязных» строк из
  CalendarContract. Сверку будит SyncAdapter своего аккаунта (раз в 15 мин,
  после перезагрузки сам) и модуль ядра, пока жив процесс. Контакты — по
  галочке, переписываются целиком (их мало).
- **Go на Android не знает часовой пояс** (считает местным UTC) — Kotlin
  передаёт его (`mobile.SetTimeZone`) до любой работы с календарём.
- **Виджет ПК — отдельное окно с ключом `…-widget`** (`nativeui`): без рамки,
  `WS_EX_TOOLWINDOW` (нет в панели задач), всегда `HWND_BOTTOM`
  (`WM_WINDOWPOSCHANGING`), таскается через `sshtunnelDrag()` из страницы,
  место — в `windows.json` после каждого перетаскивания. Открывается при
  запуске, если включён. В VPN-версии Windows окна открывает процесс окна —
  автозапуск виджета там пока не сделан (только кнопкой).

## 2026-11-03 — ТЗ 4: Карта сети, SSH, Файлы устройства

- **За основу взят vitazgio.ru** (изучен код сайта на VPS, там ничего не
  менялось): список/скачать/загрузить/папка/переименовать/удалить, непустую
  папку с первого раза не удаляем (`needsRecursive`), имя при загрузке —
  только имя (без `../`), скачивание потоком; консоль — xterm.js + fit и ряд
  клавиш; файлы телефона — «Доступ ко всем файлам» (`MANAGE_EXTERNAL_STORAGE`).
  Отличие: у сайта SFTP с паролем и свой агент телефона, у нас — одна служба
  файлов в ядре на всех платформах.
- **Служба файлов — внутри программы на порту 47835 сети устройств**
  (`mesh.Serve`, `internal/devfiles`), а не на 127.0.0.1: снаружи сети
  устройств её не достать, и она знает, кто пришёл (`mesh.Caller`: адрес
  ставит meshd по управляющему соединению, у прямого соединения — проверка
  по отпечатку). Работает и при выключенном «Пускать другие устройства к
  моим службам»: доступ решают только отмеченные папки. Протокол — HTTP по
  соединению сети устройств; докачка скачивания — Range, загрузки — куски с
  `off` во временный `.имя.sshtunnel-part`. Существующий файл не затирается
  («имя (2)»).
- **Доступ — вариант А:** открытую папку видят все устройства своей сети
  устройств (ключ сети), «можно менять» — галочка у папки. Пофамильных прав
  для устройств нет — при нужде их даёт политика meshd.
- **Android — «Доступ ко всем файлам», а не SAF:** ядро на Go работает с
  путями, SAF потребовал бы файловый слой на Kotlin. Скачивание на телефоне
  делает ядро (`/api/files/save` в «Загрузки», с докачкой): у WebView своих
  загрузок нет. Уведомление с прогрессом — `TransferNotifier`, только пока
  идёт передача. Служба VPN поднимает сервер страниц (`DeviceApps.init`),
  иначе модули приложений (служба файлов) работали бы только при открытом
  экране. Android 10 и старше («доступ ко всем файлам» появился в 11) не
  проверялся: там нужно разрешение на память — не сделано.
- **SSH на ПК — свой агент программы, а не служба OpenSSH Agent и не
  временный файл.** Служба Windows по умолчанию выключена, включить её можно
  только с правами администратора; временный файл остаётся на диске, если
  программа упадёт. Свой агент (`golang.org/x/crypto/ssh/agent`) — канал
  `\\.\pipe\ssh_tunnel-agent-<случайно>` с доступом только текущему
  пользователю, удалённые клиенты запрещены; живёт 2 минуты и закрывается.
  `ssh.exe` получает его через `-o IdentityAgent=//./pipe/…` — с обратными
  слешами OpenSSH для Windows канал не находит (проверено на 9.5p1). Берётся
  именно `System32\OpenSSH\ssh.exe`: ssh из Git Bash/MSYS каналы Windows не
  понимает. На Linux — тот же агент на сокете во временной папке 700.
- **Ключ:** ed25519, создаёт программа (`internal/sshapp`). Windows — DPAPI
  учётной записи, Android — AES-GCM ключом Android Keystore (`KeystoreSealer`
  через `mobile.SetKeySealer`), **Linux — файл 600** (keyring есть не везде,
  а сервер без рабочего стола — частый случай). Ключ сервера — TOFU: первый
  раз запоминается, смена — отказ и «Забыть ключ сервера».
- **SSH в VPN-версии Windows обслуживает окно, а не служба**
  (`addons.AppRoutes("ssh")` → `winsvc.Proxy.Local`): DPAPI пользователя и
  его рабочий стол. ssh идёт сам — в сеть устройств его ведёт адаптер. В
  обычной версии ssh идёт через одноразовый проброс 127.0.0.1 → ядро
  (`tunnel.DialApp`, решение «куда» — `core.Decide`), так адреса сети
  устройств работают и в режиме прокси.
- **Встроенный терминал — SSE для вывода и POST для ввода**, как `/events`:
  без WebSocket, одинаково в WebView2, Android WebView и браузере. Сессия без
  читателя закрывается через 2 минуты. xterm.js 5.5.0 и addon-fit 0.10.0
  (MIT) лежат в `uiassets/vendor` — без интернета.
- **Источник сети устройств для приложений — `internal/devnet`.** Окно ПК
  ставит туда `App`, телефон — `mobile.Tunnel`; приложения не знают, где
  туннель. Адреса API приложений — `addons.RegisterRoutes`: отвечают только
  у работающего приложения (403 иначе).
- **Карта сети строится на устройстве** из списка meshd: задержка — прямой
  путь или ping через сервер (кэш 10 с). Чтобы в карточке была система, meshd
  теперь отдаёт в списке устройств `os` (необязательное поле; со старым meshd
  — только платформа). Все устройства рисуются вокруг главного сервера
  (`198.19.255.254`); через какой побочный сервер пришло устройство, карта
  пока не показывает.
- **Значки страниц — по абсолютному пути `/icons/…`** (`pages.js`): страницы
  приложений лежат в `/addons/`, и относительный путь вёл в `/addons/icons/`.

## 2026-11-03 — ТЗ 6: зеркальные папки

Решено владельцем (п. 14 предыстории): двусторонние зеркальные папки, а не
«только зеркало/отправить файл» из раздела «Вопрос: заменить Syncthing».
Syncthing пока остаётся: Obsidian переводится только после двух недель
на неважной папке.

- **Сервер у папки один и он — источник правды** (`mirror.Hub`). У файла
  номер версии `Ver` (= номер изменения папки). Клиент шлёт правку с `base` —
  номером, от которого правил; не совпало → присланное ложится рядом как
  «имя (конфликт, устройство, 03.11.2026).ext», основной файл не трогается.
  Удаление с чужим `base` не выполняется (правка важнее удаления). Правка
  удалённого файла его возвращает (удалённое лежит в корзине).
- **Клиент сверяет три состояния:** диск, «с чем совпадал при прошлой
  сверке» (S) и «что на сервере» (R). Очередь без сети — это разница диска
  и S, а не отдельный список: переживает перезапуск и сутки без сервера.
  Повтор любого шага безопасен (одинаковый хеш = уже сделано), поэтому
  состояние клиента пишется раз в несколько секунд, а не после каждого файла.
- **Локальный файл меняется/удаляется, только если его хеш = S.Hash**, а
  S.Hash всегда подтверждён сервером. Замена — через отодвинутый файл
  `.~mirror-old.<имя>`: если его успели изменить в этот миг, он становится
  конфликт-копией. Оборванный проход разбирается при следующем
  (`Replica.recover`).
- **Часы не сравниваются на «раньше/позже» нигде**, только время файла на
  равенство (изменился ли). Файлы, изменённые меньше 3 с назад или «в
  будущем», перечитываются всегда (как racy git). Полная перепроверка хешей —
  раз в 6 часов.
- **Без fsnotify:** «наблюдатель» — обход папки по размеру и времени раз в
  10 с, изменения сервера — долгим опросом (приходят сразу). Без новой
  зависимости, одинаково на Windows, Linux и Android (у inotify на Android
  лимиты), несколько тысяч файлов — миллисекунды.
- **Сервер:** индекс — снимок `index.json` + журнал `journal.jsonl` с fsync
  на каждое изменение (оборванная запись теряет только недописанную строку).
  Старое содержимое перед заменой/удалением уходит в `versions/` (жёсткая
  ссылка, иначе копия) — данные сервера в папке данных программы, а не в
  раздаваемой папке (чтобы их не утащил Syncthing или кто-то ещё). Версии и
  корзина — 30 дней по часам сервера. Загрузка — кусками в `incoming/` с
  докачкой, проверка sha256 перед записью; переименование и копия не
  передаются заново (такой хеш у сервера уже есть). Правка прямо в папке
  сервера мимо программы ловится сверкой раз в 30 с и перед каждой записью
  этого файла; её прежнее содержимое не сохраняется (как и при любой ручной
  правке).
- **Сервер потерял данные** (новый `epoch`) — клиенты сверяются с ним по
  хешам с нуля; различия становятся конфликт-копиями.
- **Режимы:** «только получать» — свои правки не отправляются и не
  затираются (уходят рядом копией), удалённое у себя возвращается;
  «только отправлять» (бэкап фото) — **удаления не отправляет**.
- **Исключения по умолчанию** (`DefaultIgnore`) + свои у папки на сервере
  (клиенты получают их с индексом). Пустые папки и ссылки не передаются.
- **Служба — порт 47836 сети устройств**, как у «Файлов устройства»:
  кто пришёл, знает сеть устройств; доступ — любое устройство своей сети
  (вариант А, как у п. 13).
- **«Конфликты» — вкладка в приложении** с числом на ней, а не отдельный
  пункт главного меню (меню общее, его правят другие ТЗ). Уведомление:
  ПК — журнал окна, Android — `MirrorNotifier`. Android — «Доступ ко всем
  файлам», как у п. 13; постоянного уведомления нет.
- Тесты — `internal/mirror/mirror_test.go`: одновременная правка, удаление
  против правки, переименование, обрывы загрузки/скачивания/ответа, сервер
  недоступен сутки, сбитые часы, потеря данных сервера, оборванная замена,
  режимы, длительный (2000 файлов, 3 клиента, случайные правки и обрывы;
  `MIRROR_LONG=1` — 5000). В каждом проверяется, что ни одно записанное
  содержимое не пропало.

## 2026-11-03 — ТЗ 5: Расход трафика, Сканер сети, Общий буфер

- **Трафик считается в туннеле, без перехвата.** Встречное соединение
  оборачивается в `traffic.Wrap` (программа + путь из `core.Decide`) в тех
  же местах, где туннель его открывает (`relay.go`, `httpproxy.go`,
  `android.go`, UDP в `route.go`, `DialApp`/`DialSelf` — «ssh_tunnel»).
  Пока приложение не работает, `Wrap` отдаёт соединение как есть. Байты
  копятся в соединении и уходят в учёт кусками (256 КБ / 2 с) — замок
  общий, а Read на видео — тысячи в секунду. Хранение — `traffic.json`,
  суточные итоги «программа × путь × сеть», 92 дня.
- **Телефон: владелец — `getConnectionOwnerUid`.** На Android программу по
  порту не узнать; спрашиваем систему (это разрешено только VPN-службе) и
  только ради учёта: `tunnel.Config.OwnerOf` на решение «куда» не влияет.
  Wi-Fi / мобильная — по настоящей сети под VPN (`NetworkCallback`).
  Исключённые приложения идут мимо VPN и не считаются — так и пишем.
- **Лимит — только предупреждение** (`devnet.Warn`: журнал на ПК,
  уведомление на телефоне), один раз на 80% и на 100% за период.
- **Сканер на Windows — `SendARP`**, а не ping: отвечает любое устройство
  сети, даже с закрытым ICMP (ESP, Tuya), и сразу даёт MAC; задержка — по
  `IcmpSendEcho` (прав не нужно). На Linux/Android — ICMP-датаграмма без
  прав, иначе TCP (отказ тоже значит «живой»), MAC из `/proc/net/arp`
  (Android 10+ его не даёт — «—»). Подсеть на Android даёт Kotlin
  (`LinkProperties`): `net.Interfaces` там не работает. Больше /22 — только
  своя /24. Имена — DNS роутера, mDNS (PTR, ответ напрямую), NetBIOS. База
  OUI IEEE (MA-L, ~40 тыс., 340 КБ gzip) — внутри программы,
  `tools/mkoui`. Проверено на домашней сети: 19 устройств за ~20 с, ESP
  подписаны Espressif.
- **Буфер: ядро и наблюдатель раздельно.** Ядро (где сеть устройств)
  принимает на порту 47837 сети устройств, хранит 20 записей (содержимое —
  до 200 МБ), рассылает своим. Наблюдатель — где буфер пользователя: в
  процессе окна. В VPN-версии Windows ядро в службе (SYSTEM, сеанс 0,
  буфера не видит) — окно наблюдает и говорит со службой через её API
  (`clipshare.WatchRemote`, длинный запрос `?wait=1`). Windows — номер
  изменения буфера (без окна), форматы `CF_UNICODETEXT`, `PNG`/`CF_DIB`,
  `CF_HDROP` (один файл); Linux — `wl-paste`/`xclip`. Телефон: приём —
  `ClipboardManager` (класть из фона можно; файлы — через FileProvider),
  отправка — «Поделиться» и плитка с прозрачным окном (читать буфер можно
  только с фокусом).
- **Петли нет по устройству:** полученное никуда дальше не шлётся; своё
  наблюдатель не отправляет, если отпечаток совпал с только что положенным.
  Повтор записи с тем же id не принимается.
- **Участие = выключатель фонового приложения** на каждом устройстве: модуль
  не работает — службы на порту нет, и другие сюда не шлют.
- Общие файлы не правились: каталог — `addons/catalog_tools5.go`, импорт
  пакетов — `addons/devapps/tools5.go`.

## 2026-11-03 — ТЗ 8: команды, MCP, свои приложения из файла

- **Всё — обёртки над API, своей логики нет** (`src/internal/apicli`).
  Команды и MCP читают `api.json` и ходят тем же ключом, что окно. Новый
  адрес в API сразу становится командой (`слова пути ключ=значение`) и
  инструментом MCP (`api_<путь>`) — по самоописанию `GET /api`. Понятные
  команды/инструменты (`state`, `tunnel on|off`, `rules add …`) — сверху,
  для частого.
- **`/api/rules`** — правила активного сервера отдельным адресом. Не новая
  логика, а те же поля профиля, что в `/api/config`, — но без ключей и
  остальных настроек: так «менять правила» можно дать своему приложению и
  нейросети, не отдавая всё. Android (`AndroidApi.kt`) его пока не отдаёт.
- **Опасное — поле `confirm` в самоописании** (карта `confirm` в
  `webui/api.go`, по пути): MCP пишет «ОПАСНО — спроси человека» и
  `destructiveHint`. `/api/state` помечен целиком (mesh:false), а понятный
  `set_tunnel` — нет: включить/выключить обход безопасно.
- **Галочка MCP** — `config.mcpEnabled`, по умолчанию выкл., проверяется на
  каждом вызове инструмента (не на запуске): включил — работает без
  перезапуска нейросети. Список инструментов отдаётся и при выключенной,
  вызов отвечает «включи галочку». Это выключатель согласия, а не защита:
  ключ из `api.json` и так у пользователя.
- **`ssh_tunnel.exe` оконный** (`-H windowsgui`) — для команд он
  подключается к консоли родителя (`AttachConsole`), если вывод не
  перенаправлен. PowerShell оконную программу не ждёт: ответ может прийти
  после `PS>`; с `| Out-String` или `$x = …` ждёт. Отдельный консольный exe
  не заводили — в релизе один файл. MCP консоль не трогает (stdio — трубы).
- **Свои приложения: песочница — CSP `sandbox` на ответе + iframe
  `sandbox` без `allow-same-origin`.** Непрозрачный origin: ни окна
  программы, ни её ключа, ни localStorage. Отдельный порт не нужен.

- **Ключ приложения в пути страницы** (`/custom/<id>/<ключ>/…`): им

- **Разрешения → адреса** (`permissions` в `addons/custom.go`):
  префикс пути + методы, `$` — точное совпадение. Всегда можно `GET /api` и
  свои данные `/api/app/data` (1 МБ, `data.json`). Тест на образце
  проверяет, что без `devices` `/api/mesh` — 403.
- **Без нативного кода — белый список расширений** в архиве; exe/dll/so и

  кода в ядре фону нечего делать.

## 2026-11-03 — ТЗ 9: настоящие адреса вместо подставных (DNS)

- **По умолчанию наш DNS отдаёт настоящие адреса, fake-IP — галочкой
  «Подставные адреса» (`config.fakeIP`, выкл.).** Причина: на любое имя
  `198.18.x.x`, а программы с защитой от SSRF (DeepSeek Harness `web_fetch`:
  «URL hostname resolves to a non-public IP address»), клиенты со списками
  по IP, часть браузерных политик считают такой адрес внутренним и не
  соединяются. Исключение программы не помогало: DNS в Windows спрашивает
  системная служба, программа всё равно видела подставной адрес.
- **Имя «через сервер» разрешается через сервер** — DNS поверх TCP по
  SSH-каналу к `1.1.1.1`, запасной `8.8.8.8` (`tunnel.LookupViaServer`):
  провайдер не видит ни имени, ни ответа, подменить нечем; anycast отдаёт
  CDN рядом с сервером. Не DNS самого VPS — у него бывает кривой резолвер.
  Ответы помнятся минуту (TTL ответа системе — 60 с, у подставных остаётся
  10). Имена «напрямую» и локальные — DNS настоящей сети, как раньше.
  Решение, чем отвечать, — только `core.DecideDNS` (новый ответ `DNSServer`).
- **«Куда» без подставного адреса:** имя соединения — из первых байтов
  (`core.SniffHost`: SNI в TLS ClientHello, Host в HTTP; `core.SniffQUIC`:
  SNI из пакета Initial, ключи по RFC 9001/9369), иначе — таблица «адрес →
  имя» из ответов нашего DNS (`tunnel.LearnName`, бывшая таблица «всегда
  напрямую», потолок 16384). SNI сильнее таблицы: на одном адресе CDN много
  имён. Дальше то же `core.Decide` (имя — в `Conn.Name`). Ждём первые байты
  не дольше 300 мс; на портах, где первым говорит сервер (21, 22, 25, 110,
  143, 587, 3306, 5432, 5900, 23), не ждём. С галочкой fake-IP имя не ищется
  — его приносит адрес, как раньше. Соединение с именем, разрешённым нашим
  DNS, в журнале не помечается утечкой DNS; имя только из SNI (браузер с
  «безопасным DNS») — помечается, как и раньше.
- **«Всегда настоящий адрес»** (`config.realIPHosts`) — общий для всех
  серверов список, как и галочка (это свойство DNS устройства, а не сервера).
  Через `/api/config`, `/api/rules` (`list:"realip"`, `{"fakeIP"}`),
  команды `rules fakeip|add realip`, MCP.
- **Смена галочки или списка — `Machine.ReapplyDNS`**: тот же режим заново с
  гигиеной `core.DNSModeChanged` (таблица подставных адресов и ответов через
  сервер, DNS-кэш системы, соединения из адаптера, пересчёт решений) — как
  при переключении режима, без перезагрузки.
- **IPv6: AAAA не отдаём** (пустой ответ, как раньше): адреса шестой версии
  через сервер не разрешаем, а у адаптера без IPv6 соединение по ним ушло
  бы мимо туннеля — утечка. Запрос через сервер — только A. HTTPS-записи
  тоже пустые: QUIC через SSH всё равно не идёт.

## 2026-11-07 — настройки рекламы, выбор папки и старые серверы зеркал

- **Блокировка рекламы остаётся только плагином.** Из общего `index.html`
  удалены её страница и кнопка в настройках; API, конфиг и `addons/adblock.html`
  не меняются. Поле `status.adBlock` по-прежнему означает VPN-версию для
  настроек точки доступа и DNS — переименование потребовало бы ломать API.
- **Системный выбор папки получает владельцем активное окно Windows.** У
  `SHBrowseForFolderW` больше нет нулевого `Owner`: диалог не должен теряться
  за окном VPN ни во встроенном режиме, ни при открытии плагина отдельно.
- **Старый сервер зеркал не получает записи пустых папок.** Ответ `/index`
  нового сервера содержит `dirs:true`; если поля нет, клиент синхронизирует
  файлы, но пропускает каталоги. Раньше старый сервер отвечал «плохой путь или
  хеш», а очередь пустых папок навсегда оставалась жёлтой. В ожидающем статусе
  интерфейс теперь показывает и текст ошибки, если она всё же есть.

## 2026-11-07 — возврат плагина из отдельного окна

- **Переключатель «Здесь / В окне» доступен в обоих режимах.** Раньше в
  отдельном окне он скрывался, поэтому сохранённый режим нельзя было вернуть.
  «Здесь» сохраняет выбор и закрывает отдельное окно; следующий запуск — внутри
  приложения. Главная страница и список плагинов получают изменение через
  `BroadcastChannel`, чтобы быстрый доступ не использовал старый кэш.
