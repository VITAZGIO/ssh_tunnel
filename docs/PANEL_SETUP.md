# Веб-панель для VPS (ssh_tunnel_panel)

Отдельная программа. Ставится **на сам сервер** и заводит клиентов по
кнопке — без консоли, без ручных `useradd` и правки `authorized_keys`.

## Чем отличается от локальной панели

`ssh_tunnel_linux -web` — окно программы на компьютере клиента: управляет
только своим собственным подключением, доступна по токену в адресе и
только с этой машины.

`ssh_tunnel_panel` — отдельная программа на самом VPS. Она не подключается
никуда сама, а управляет тем, **кому разрешено подключаться к этому
серверу**: заводит и удаляет клиентов, у каждого свой unix-пользователь и
свой ключ, показывает трафик и то, кто сейчас на связи. Смотрит в интернет,
поэтому вход — логин и пароль, а не токен в ссылке.

Если тебе нужен только один компьютер, которому доверяешь, и настраивать
его будешь сам, — панель необязательна, хватит
[ручной настройки](SERVER_SETUP.md). Панель нужна, когда клиентов несколько
(свои разные устройства, или ты раздаёшь доступ другим людям) и заводить
каждого руками через SSH надоедает.

## Панель работает от root — и это важно понимать

Чтобы заводить и удалять системных пользователей, панели нужны права root.
Это не забытая мелочь — без root часть её работы просто невозможна. Юнит
systemd сужает ей всё остальное (`PrivateTmp`, `ProtectSystem=true` — `/usr`
и `/boot` только для чтения, `NoNewPrivileges`, защита настроек ядра),
но сам факт «процесс с интернета работает под root» никуда не девается.
Из этого следуют три практических вывода:

1. **Пароль** — сразу после первого входа смени одноразовый пароль на свой,
   длинный и уникальный. Перебор паролей панель тормозит сама (растущая
   задержка и блокировка после нескольких неудач), но это не замена
   нормальному паролю.
2. **Домен и сертификат** — не держи панель голым HTTP на порту, открытом в
   интернет. Либо свой домен с TLS через reverse proxy, либо встроенный
   автосертификат (ниже) — но не голый HTTP без домена и сертификата.
3. **Ограничение по адресам**, если оно возможно — firewall или reverse
   proxy, пускающий на порт панели только с твоего адреса или из VPN. Панели
   для этого специальных флагов не нужно — это делает то, что стоит перед
   ней (ufw, nginx, Tailscale/NetBird).

## Установка одной командой

Один блок — вставить целиком на свежем сервере под root. Ничего скачивать
заранее не нужно: сам заберёт бинарь под архитектуру сервера с GitHub,
поставит службу и покажет адрес панели и пароль.

**Вариант 1 — без своего домена.** Панель слушает только `127.0.0.1:47823`,
снаружи её открывать не нужно — заходить через SSH-туннель или добавить
домен и nginx/Caddy позже (см. «Домен и TLS» ниже):

```bash
curl -fsSL https://raw.githubusercontent.com/VITAZGIO/ssh_tunnel/main/packaging/panel/install.sh \
  | sudo bash -s -- --lan --ssh-host=АДРЕС_ЭТОГО_СЕРВЕРА
```

**Вариант 2 — со своим доменом.** Домен должен уже указывать A-записью на
этот сервер — тогда панель сама получит сертификат Let's Encrypt и будет
доступна по HTTPS сразу:

```bash
curl -fsSL https://raw.githubusercontent.com/VITAZGIO/ssh_tunnel/main/packaging/panel/install.sh \
  | sudo bash -s -- --domain=panel.example.com
```

В обоих случаях в конце команда сама печатает, по какому адресу открывать
панель, и одноразовый пароль для входа — их же в любой момент можно
посмотреть так:

```bash
journalctl -u ssh_tunnel_panel -n 50
```

Если уже есть свой reverse proxy (nginx/Caddy) и хочется завести панель
за ним без открытого наружу порта — третий вариант, без `--lan` и без
`--domain` (это режим по умолчанию, подробнее — «Домен и TLS» ниже):

```bash
curl -fsSL https://raw.githubusercontent.com/VITAZGIO/ssh_tunnel/main/packaging/panel/install.sh \
  | sudo bash -s -- --ssh-host=АДРЕС_ЭТОГО_СЕРВЕРА
```

Уже скачал бинарь сам (например, собрал из исходников) — путь к нему первым
аргументом после `--`:

```bash
sudo bash install.sh ./ssh_tunnel_panel --lan --ssh-host=АДРЕС_СЕРВЕРА
```

## Первый вход

При первом запуске, если пользователей ещё нет, панель сама заводит учётку
`admin` со случайным одноразовым паролем и печатает его в журнал. Она
потребует сменить этот пароль сразу после первого входа — он больше нигде
не хранится, и если он потерян, единственный выход — удалить
`/etc/ssh_tunnel_panel/users.json` и перезапустить службу
(`systemctl restart ssh_tunnel_panel`): панель заведёт новую одноразовую
учётку, как при первом запуске.

## Книга

В самой панели, «Настройки» → «Книга», есть справка по панели: список глав и
поиск по всему тексту. Она встроена в программу и работает без интернета; язык
— тот же, что выбран в панели. Рядом с заголовками разделов у значка «?»
(нажми на него) есть ссылка «Подробнее в Книге», если у раздела есть глава.
Текст глав лежит в репозитории, `docs/book-panel/<ru|en>/NN-имя.md`; в сборку
его копирует `cd src/internal/panel && go generate`, а тест следит, чтобы копия
не разошлась с источником. Ручка — `GET /api/book?lang=ru|en`.

## Домен и TLS

Два пути, оба поддержаны без переустановки — просто разными флагами:

**За nginx/Caddy (по умолчанию).** Панель слушает только
`127.0.0.1:47823`, сертификат и домен — забота реверс-прокси перед ней.
Типичный конфиг nginx:

```nginx
server {
    listen 443 ssl;
    server_name panel.example.com;
    ssl_certificate     /etc/letsencrypt/live/panel.example.com/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/panel.example.com/privkey.pem;

    location / {
        proxy_pass http://127.0.0.1:47823;
        proxy_set_header Host $host;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}
```

Заголовок `X-Forwarded-Proto` важен: по нему панель понимает, что соединение
пришло по HTTPS, и ставит cookie сессии с флагом `Secure`.

**Встроенный автосертификат**, если отдельного реверс-прокси на машине нет:

```bash
sudo bash install.sh ./ssh_tunnel_panel --domain=panel.example.com
```

Панель сама получает и продлевает сертификат Let's Encrypt
(`golang.org/x/crypto/acme/autocert`), слушает `:443` для панели и `:80` —
только для проверки домена, которую требует Let's Encrypt. Домен должен уже
смотреть A-записью на сервер до запуска — иначе получить сертификат не
получится.

## Смена порта

Порт задаётся флагом `-listen` (по умолчанию `127.0.0.1:47823`). Поправь
`ExecStart` в `/etc/systemd/system/ssh_tunnel_panel.service`:

```bash
sudo sed -i 's|^ExecStart=.*|ExecStart=/usr/local/bin/ssh_tunnel_panel -listen 127.0.0.1:8443|' \
  /etc/systemd/system/ssh_tunnel_panel.service
sudo systemctl daemon-reload
sudo systemctl restart ssh_tunnel_panel
```

При `--domain` порт не имеет значения — панель всегда слушает `:80` и `:443`.

## Адрес для подключения клиентов

Отдельно от адреса самой панели: клиенты подключаются по SSH к серверу, а не
к веб-панели. С `--domain` панель берёт этот адрес из того же домена
автоматически. Без `--domain` (`--lan` или обычный режим за реверс-прокси)
задай его явно при установке:

```bash
sudo bash install.sh ./ssh_tunnel_panel --lan --ssh-host=203.0.113.10
```

Без этого адреса панель заведёт клиента, но не сможет собрать для него
готовый конфиг (ТЗ-10) — только сообщит, что адрес не задан.

## Как добавить первого клиента

1. Открой панель, войди, смени одноразовый пароль.
2. На главном экране — «+ Добавить клиента»: имя устройства («Ноутбук»,
   «Телефон») и тип (Windows, Linux, Android).
3. После создания панель сама покажет готовый конфиг: QR-код и под ним
   «Скопировать ссылку» (ссылка `sshtunnel://`, формат — `docs/IMPORT_LINK.md`),
   «Скопировать» и «Скачать файл» — плюс адрес, порт, пользователя и ключ
   текстом, если нужно вписать руками. QR и ссылка есть **только в этот
   момент**; потом у клиента остаётся кнопка «Показать настройки» — с файлом
   и полями, но без QR.
4. На заведённом устройстве — импортировать: на телефоне отсканировать QR
   (в приложении или камерой), на ПК вставить ссылку кнопкой «Вставить»;
   файл по-прежнему открывается кнопкой «Импорт».

Дальше в списке клиентов видно трафик, число активных сессий и время
последнего подключения; кнопками — заморозить (временно запретить вход,
не удаляя ключ из хранилища панели), отключить (оборвать текущие сессии, не
трогая ключ) и удалить (стереть пользователя и ключ насовсем).

## Ёмкость сервера

Программа держит 4 SSH-соединения на устройство, а `sshd` по умолчанию
(`MaxStartups 10:30:100`) начинает отбрасывать входы, когда их ждёт больше
десяти, — поэтому уже три устройства, подключающиеся разом, мешали друг
другу. Панель при каждом запуске выставляет `MaxStartups` под число устройств
из «Настройки → Ёмкость сервера» (по умолчанию 30, то есть `120:30:240`):
пишет блок в начало `/etc/ssh/sshd_config`, гасит другие объявления
`MaxStartups`, проверяет всё `sshd -t` и только потом перечитывает `sshd`.
Уже подключённых это не касается.

## Сеть устройств

«Настройки» → «Сервер сети»: установка своего `meshd`. Серверов в сети может
быть сколько угодно, главного нет: у каждого свой `meshd`, устройства держат
связь со всеми серверами, профили которых у них есть (тот же ключ сети).
«Сети» → «Серверы сети»: этот сервер, другие серверы сети по рассказам
устройств (и такие ли у них правила доступа), серверы, которые панель
советует устройствам. Правила доступа, журнал, имена и удаление действуют
только на этом сервере — панель так и пишет. Старый способ — «побочный»
сервер, проброс к `meshd` другого — работает и помечен «старый способ»;
перейти с него на свой `meshd` — «Настройки» → «Перейти на свою службу
сети». Схема сети, устройства с качеством связи и переименованием — там же.
В карточке устройства — «Одобрить» / «Отклонить» (если в «Сетях» включено
«Новые устройства — после одобрения»), «Заморозить в сети» и цепочка выхода,
которую панель советует устройству (оно может её поменять — панель покажет
его значение). Одобрение и заморозка тоже только на этом сервере; нужен
`meshd` версии 5 («Обновить meshd»).

API панели для этого (вход по сессии, ошибка — 400 `{"error"}`):
`POST /api/mesh/net/approval` `{"net","on"}`, `POST /api/mesh/approve`
`{"net","device"}`, `POST /api/mesh/freeze` `{"net","device","on"}`,
`POST /api/mesh/exit` `{"net","device","entry":"адрес:порт","via":[…]}` →
`{"ok":true,"exit":{entry,via,t,by,byId}}`. В `GET /api/mesh/state` у сети —
`approval`, у устройства — `pending`, `frozen`, `profiles`
(`[{k,n,a,v,t,b}]`: ключ, имя, активный, цепочка, время, кто задал) и
`exitSet` (что задала эта панель). `POST /api/mesh/check` может ответить
`reason` `"pending"` или `"frozen"`. Простой режим доступа сохраняется одним
запросом `POST /api/access/simple` `{"enabled","groups","rules","clients":{"<id
клиента>":[группы]}}`: всё проверяется до первой записи.

Подробно, с порядком обновления нескольких серверов, — в [MESH.md](MESH.md).

## Плагины сервера

Вкладка «Плагины»: сервер сам становится участником сети устройств —
зеркальные папки, общая папка («Файлы устройства»), общий буфер и
резервные копии работают прямо на сервере, через тот же код, что их
обслуживает на устройствах. Ещё три плагина — история машин, общий список
блокировки рекламы и проверка сайта с сервера (ниже).

Плагины живут в отдельном процессе `ssh_tunnel_node`, без прав root: своя
учётная запись системы (как у `meshd` — `DynamicUser` в systemd), своя папка
данных `/var/lib/ssh_tunnel_node`. Панель только ставит, запускает,
останавливает и настраивает его через управляющий сокет
`/run/ssh_tunnel_node/control.sock` — root достаёт его в обход прав файла,
больше никто.

Кто к плагину пришёл, узнаёт `meshd` (как и для любого порта самого
сервера): подделать это с другой машины или другого пользователя системы
нельзя. Пока сеть устройств не поставлена или её версия слишком старая (нет
ответа на вопрос «кто звонит»), плагины никого не пускают — об этом видно
в карточке хоста.

- «Поставить хост плагинов» скачивает `ssh_tunnel_node` со страницы этого
  релиза и поднимает службу — после установки появляются переключатели
  плагинов, общая квота места на диске и список сетей.
- Для каждой сети — её зеркальные папки (имя, квота, занятое место,
  конфликты), занятое место общей папки, записи общего буфера. Квота —
  общая у всех плагинов сети и всех сетей вместе: переполнилось — новые
  данные отклоняются понятной ошибкой на устройстве, уже записанное не
  портится.
- «Снять» останавливает и убирает службу; данные (папки, буфер) остаются,
  пока не отмечена галочка «Удалить и данные плагинов» — тогда их не
  восстановить.
- **«Что мешает плагинам»** — панель сама сверяет «Сервер в сети устройств»
  и права доступа с портами включённых плагинов (47835 файлы, 47836 папки,
  47837 буфер, 47838 копии, 47844 машины, 47845 блокировка рекламы, 47846
  проверка сайта). Закрытые порты сервера открываются одной
  кнопкой — только порты плагинов: каждого, кто пришёл, плагин опознаёт
  сам. Права доступа панель сама не меняет — только называет, у кого нет
  правила к `@servers`. На побочном сервере опознание не работает — панель
  так и пишет.
- У каждой сети — когда устройства последний раз обращались к каждому
  плагину; квоту зеркальной папки можно поменять прямо в строке папки.
  Безымянная сеть показана как «Сеть N».
- **Резервные копии** устройств: размер, число версий, «держать», время
  последней копии; «Удалить» убирает копию со всеми версиями. Одинаковое
  содержимое хранится один раз (внутри одного пользователя). Читать копию
  может только её устройство и устройства того же SSH-пользователя.
- Сеть удалили в «Сетях», а данные плагинов остались — карточка помечена
  «сеть удалена, данные остались» и кнопкой «Удалить данные». Сами по себе
  они не стираются никогда; живую сеть так стереть нельзя.

### Машины, блокировка рекламы, проверка сайта

Три плагина, которые делают на сервере то, что устройство не может делать
хорошо: оно не включено круглосуточно или сидит в другой сети.

- **«Машины: история»** — устройства с плагином «Машины» каждые 30 секунд
  присылают сюда показания своих машин (процессор, память, диск,
  температура, в сети ли). Сервер сам машины не читает: их адреса, пароли и
  токены остаются на устройствах, а первым звонить устройству сервер не
  может. Поэтому история без дыр будет у машин, которые читает устройство,
  включённое всегда (домашний сервер или сама машина с ssh_tunnel и
  источником «это устройство»); ноутбук, который выключали, увидит её с
  сервера. Хранится «Хранить историю машин» дней (30 по умолчанию) и
  считается в общей квоте. У сети видно, кто присылает какие машины,
  «Стереть историю» её стирает. Чужие устройства сети видят историю
  только если у присылающего включено «Показывать мои машины всем».
- **«Блокировка рекламы: общий список»** — один список на сервер:
  источники (ссылки на списки hosts или adblock), свои «Блокировать
  всегда» и «Не блокировать никогда», время обновления, число имён и
  сколько устройств забирали его за сутки. Источники качаются раз в сутки
  и по «Обновить сейчас»; не скачался ни один — раздаётся прежний список.
  Устройства с плагином «Блокировка рекламы» забирают его раз в 15 минут
  и блокируют сами, как раньше; без связи с сервером у них действует
  последний список.
- **«Проверить сайт с сервера»** — те же шаги, что у плагина на
  устройстве (DNS → подключение → защищённое соединение → ответ), только из
  сети сервера: на устройстве это колонка «с сервера», в панели — поле и
  кнопка. Это не прокси: только имена в интернете на порту 443, запрос —
  один GET «/» без тела, локальные и закрытые адреса (и имена, которые в
  них разрешаются) не проверяются, с одного устройства — не больше 5
  проверок подряд и дальше по одной в 10 секунд.

Двум последним плагинам нужен выход в интернет, поэтому у службы
`ssh_tunnel_node` больше нет ограничения `IPAddressAllow=localhost`; порты
плагинов по-прежнему слушают только 127.0.0.1.

### Nginx Proxy Manager и адреса `.mesh`

Контейнер Docker на сервере (например, Nginx Proxy Manager) **сейчас не
достанет** до устройства по адресу `ноутбук.mesh` или `198.19.x.x`. Не
хватает трёх вещей:

1. **Имени.** Имена `.mesh` знает только DNS самой программы на каждом
   устройстве; на сервере и в контейнерах их никто не разрешает.
2. **Пути.** У сервера нет сетевого интерфейса в сети устройств: адреса
   198.19.0.0/16 не маршрутизируются, весь трафик к устройствам идёт через
   `meshd` по его протоколу (вызов `dial`), а `meshd` слушает только
   127.0.0.1 — из моста Docker его не видно.
3. **Права.** Звонить устройству может только устройство сети, вошедшее
   через SSH: `meshd` сверяет пользователя системы, которому принадлежит
   соединение, с SSH-пользователем устройства. Сам сервер первым звонить
   устройствам не может (проверка доступа так и отвечает: «server cannot
   initiate»).

Нужна отдельная доработка: пересылка на сервере «порт на мосту Docker →
устройство:порт» через `meshd`, со своей учётной записью и правилом в
«Доступе» (это `meshd`, `internal/mesh` и сама панель — вне плагинов). До
неё NPM держат на устройстве внутри сети (домашний сервер) или проксируют
на адрес устройства в его локальной сети.

## Выход сервера через другой сервер

**Настройки → «Выход сервера → через сервер Б»**: собственный трафик этого
сервера (обновления пакетов, контейнеры, пользователи туннеля, выходящие
здесь) уходит через другой сервер ssh_tunnel. Вход снаружи (SSH на этот
сервер, эта панель, устройства, сеть устройств) не затрагивается — отвечает
тем же путём, каким пришёл.

Как включить: в панели сервера Б создать обычного клиента («Устройства →
Добавить») и вставить сюда его ссылку `sshtunnel://…` (её показывают один
раз сразу после создания). Панель сама ставит на этот сервер Linux-клиент
VPN той же версии, что и она сама (из того же релиза GitHub, с проверкой
контрольной суммы), проверяет по SSH, что сервер Б не выходит в интернет
через этот же сервер (петля), и применяет маршруты.

После применения — 60 секунд, чтобы подтвердить кнопкой, что панель всё ещё
отвечает (открыть её в новой вкладке или с телефона). Без подтверждения
отдельный таймер `systemd`, не зависящий ни от панели, ни от сети, снимает
всё как было — и после перезагрузки или падения панели посреди применения
тоже.

Если сервер Б пропал: в карточке выбирается, что делать — «сервер без
интернета» (по умолчанию, вход снаружи работает, собственный трафик никуда
не уходит) или «выход напрямую». Подробно про устройство — в [VPN.md](VPN.md).

## Обновление

**Настройки → Версия панели → «Проверить обновления»**: если вышла новая
версия, появится кнопка «Обновить до …». Панель сама скачает свой файл из
релиза на GitHub, сверит его с `SHA256SUMS.txt` того же релиза, подменит
`/usr/local/bin/ssh_tunnel_panel` и перезапустится — примерно за минуту,
страница обновится сама, входить заново не нужно. Подключённые устройства
это не затрагивает.

Подменяет файл не сама панель (служба запущена с `ProtectSystem`, `/usr` ей
только на чтение), а временная служба `systemd-run` — так же, как ставится
meshd.

Версии до 1.7.3 этой кнопки не имеют — их один раз обновляют командой под
root, дальше можно из настроек:

```bash
case $(uname -m) in aarch64|arm64) f=ssh_tunnel_panel_arm64;; *) f=ssh_tunnel_panel;; esac; curl -fsSL -o /tmp/ssh_tunnel_panel "https://github.com/VITAZGIO/ssh_tunnel/releases/latest/download/$f" && install -m 755 /tmp/ssh_tunnel_panel /usr/local/bin/ssh_tunnel_panel && systemctl restart ssh_tunnel_panel
```

## Как снять панель

```bash
sudo systemctl disable --now ssh_tunnel_panel
sudo rm /etc/systemd/system/ssh_tunnel_panel.service
sudo systemctl daemon-reload
sudo rm /usr/local/bin/ssh_tunnel_panel
```

Это останавливает панель и убирает её саму, но не трогает уже заведённых
клиентов — их unix-пользователи и ключи в `authorized_keys` остаются
рабочими, а ограничения sshd (`Match Group sshtunnel` в
`/etc/ssh/sshd_config`, между строк `# BEGIN ssh_tunnel_panel` и
`# END ssh_tunnel_panel`) продолжают действовать. Чтобы убрать полностью:

```bash
# Удалить всех клиентов панели (замени tun_* на реальные имена из
# `getent passwd | grep tun_`, если хочешь удалить не всех):
for u in $(getent passwd | cut -d: -f1 | grep '^tun_'); do
  sudo userdel -r "$u"
done

# Убрать блок ограничений из sshd_config (он между этими двумя строками)
# и группу:
sudo sed -i '/# BEGIN ssh_tunnel_panel/,/# END ssh_tunnel_panel/d' /etc/ssh/sshd_config
sudo systemctl reload ssh
sudo groupdel sshtunnel

# Данные самой панели (пользователи панели, список клиентов, кеш сертификата):
sudo rm -rf /etc/ssh_tunnel_panel
```

## Флаги

| Флаг | По умолчанию | Что делает |
|---|---|---|
| `-listen` | `127.0.0.1:47823` | адрес, который слушает панель без `-domain` |
| `-domain` | — | включает HTTPS со встроенным автосертификатом на этот домен |
| `-ssh-host` | берётся из `-domain` | адрес, который клиенты используют для SSH-подключения к серверу |
| `-ssh-port` | `22` | SSH-порт сервера — попадает в конфиг клиента |
| `-public-url` | собирается из `-domain` | адрес самой панели — попадает в конфиг клиента (ТЗ-12) |
| `-data-dir` | `/etc/ssh_tunnel_panel` | папка с учётными записями, клиентами и кешем сертификатов |
