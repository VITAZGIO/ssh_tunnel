# Версия для Android

Приложение написано, но **на живом телефоне ещё не проверялось**. Всё, что
можно было проверить без устройства, проверено; остальное честно перечислено
в конце.

## Почему нельзя просто пересобрать то же самое

Версии для Windows и Linux работают как **локальный прокси**: они поднимают
SOCKS и HTTP на `127.0.0.1`, а система направляет туда трафик приложений.
В Android такого способа нет:

- общесистемной настройки прокси, которую можно поменять из приложения, там
  не существует — прокси в настройках Wi-Fi действует только на текущую сеть
  и только на часть приложений;
- переменные среды на Android никто не читает;
- единственный настоящий способ увести трафик — `VpnService`, то есть
  виртуальный сетевой интерфейс.

Система отдаёт приложению файловый дескриптор, в который сыплются **сырые
IP-пакеты**. Значит, нужен свой стек TCP/IP в пользовательском пространстве.
Это и есть та часть, которой не было.

## Как устроено

```
приложения телефона
      │  система заворачивает трафик по своим правилам
      ▼
  VpnService  →  tun (файловый дескриптор)
      │
      ▼
  сетевой стек gVisor        ← android/core
      │  из пакетов собраны соединения: адрес и порт известны
      ▼
  tunnel.ServeConn           ← ядро из src/, оно же на Windows
      │  SSH direct-tcpip
      ▼
  твой сервер → интернет
```

Ядро туннеля переиспользуется целиком: пул SSH-соединений, keepalive,
переподключение, проверка ключа сервера, правила маршрутизации, лог и
счётчики — всё то же самое, что работает на компьютере.

## Из чего состоит

| Где | Что |
|---|---|
| `android/core` | сетевой стек: пакеты → соединения, подставные адреса, DNS |
| `android/core/mobile` | прослойка между Go и Kotlin |
| `android/app` | приложение: WebView с общим экраном, мост, VPN-служба, плитка |
| `.github/workflows/android.yml` | сборка APK |

Приложение и ядро — разные языки, поэтому между ними узкая прослойка. Связка
Go с Java умеет передавать только простые значения, так что настройки идут
плоскими параметрами, а обратная связь — через интерфейс, который реализует
Kotlin: пометить сокет, показать состояние, дописать строку в журнал,
разрешить имя средствами системы.

## Что проверено

Пакет `android/core` — сетевой стек поверх дескриптора от `VpnService`.
Проверки идут на **настоящем** tun-устройстве: пакеты формирует ядро Linux,
SSH-сервер поднят по-настоящему, соединение до цели открывает он же.

| Что проверяется | Тест |
|---|---|
| Пакеты превращаются в соединение, данные не бьются | `TestПакетыСтановятсяСоединением` |
| Вся цепочка до SSH-сервера и обратно | `TestЦепочкаЦеликом` |
| 512 КБ проходят байт в байт | `TestБольшойОтвет` |
| Список «всегда напрямую» действует и здесь | `TestСписокНапрямую` |
| UDP отбивается сразу, а не по таймауту | `TestUDPОтбрасываетсяБыстро` |
| Имя доходит до ядра, а не подставной адрес | `TestИмяДоходитДоЯдра` |
| На запрос AAAA ответ пустой, но успешный | `TestОтветНаAAAAПустой` |
| Локальному имени подставной адрес не выдаётся | `TestИмяМимоТуннеляБезРезолвераОтклоняется` |

```bash
cd android/core
go test ./... -race
```

Тестам нужны `/dev/net/tun` и право создавать интерфейсы; без них проверки,
которым нужно устройство, пропускаются, а не падают.

## Принятые решения

**Отдельный модуль.** Сетевой стек тянет gvisor и требует Go 1.26, а настольной
версии это не нужно — она остаётся на Go 1.22 и трёх зависимостях. Путь модуля
начинается с `sshtunnel/`, поэтому пакеты `internal/` основного модуля остаются
доступными: правило внутренних пакетов смотрит на путь импорта.

**UDP не проходит и не будет.** SSH переносит только TCP — это свойство
протокола. Важно не молчать: если просто выбрасывать пакеты, отправитель ждёт
до таймаута, и браузер вместо быстрого отката с QUIC на TCP выдаёт ошибку.
Стек отвечает «порт недоступен», и клиент переключается за доли миллисекунды —
это измерено в тесте. Приложениям, которым UDP нужен по-настоящему (звонки,
игры), место в списке исключений: там их трафик пойдёт мимо туннеля целиком.

**Отбор приложений делает система.** `VpnService.Builder` умеет
`addAllowedApplication` и `addDisallowedApplication` — те же три режима, что в
настройках на компьютере, только следит за ними Android. Поэтому определять
процесс по сокету (`internal/procinfo`) на телефоне не нужно вовсе, а правила
по программам к трафику из tun не применяются: он уже отобран. Правила по
адресам — «локальная сеть напрямую» и «всегда напрямую» — работают как обычно.

**Локальная сеть не заводится в маршруты.** На Android 13+ есть
`excludeRoute()`, и домашние подсети просто не попадают в туннель — на уровне
ядра, без единой проверки в коде.

**DNS отвечаем сами, подставными адресами.** Запросы приходят по UDP, а нести
их через SSH нечем. Вместо пересылки имени выдаётся адрес из
`198.18.0.0/15`, пара запоминается, и когда приложение приходит с соединением
на этот адрес — наверх уходит **имя**. Разрешает его сервер, как и на
компьютере, а наружу с телефона не уходит ни одного запроса: в сети не видно,
какие сайты открываются. Заодно продолжают работать правила по именам.

На запрос адреса IPv6 и на запись HTTPS отвечаем пусто, но успешно. Второе
важнее, чем кажется: в записи HTTPS сайт сообщает, что умеет HTTP/3, и ответ на
неё подтолкнул бы браузер к QUIC — то есть к UDP, который через SSH не пройдёт.

Именам, которым положено идти мимо туннеля, подставной адрес не выдаётся: они
разрешаются по-настоящему, средствами системы. На Android для этого нужен
резолвер из Kotlin-части — файла `/etc/resolv.conf` там нет.

**Соединения программы помечаются как идущие мимо туннеля.** Без этого не
работает вообще ничего: система заворачивает внутрь весь трафик, включая наш
собственный, и соединение с сервером ушло бы в себя же. Помечаются и
соединение с сервером, и прямые соединения мимо туннеля. На Windows и Linux
поле пустое и ничего не меняет.

**Телефон догоняет ПК (ТЗ 20).** Три вещи, сделанные раньше для компьютера,
работают и на телефоне — тем же общим кодом, без своих правил:

- *Несколько серверов сети устройств.* Телефон держит связь со всеми своими
  серверами, у которых тот же ключ сети и включена сеть (как на ПК —
  `config.Config.MeshServers`); «только через этот сервер»
  (`meshOnlyThis`) — ни одного лишнего. Список серверов приложение отдаёт
  ядру целиком (`Tunnel.SetProfiles`), выбирает общий код. Дополнительный
  сервер — лёгкое соединение (`tunnel.MeshLinks`): SSH keepalive и «тихий»
  пинг meshd раз в 60 с. По оценке ТЗ 12 это ≈ 1,2× к батарее при двух
  серверах; на телефоне не измерялось. Соединения есть, только пока
  включена кнопка «Сеть устройств».
- *Цепочка выхода.* «Выход через» в настройках сервера — тот же, что на ПК
  (`exitVia`, до двух серверов, `POST /api/profile/exit`). В интернет — только
  через последний сервер; имена с подставными адресами открывает он же, так
  что и DNS идёт через него. Запасного пути нет: пока сервер цепочки лежит,
  интерфейс VPN ловит пакеты, а соединения получают отказ — мимо цепочки не
  уходит ничего (`TestЦепочкаБезУтечкиПокаСерверЛежит`). Строка «Выход
  через: …» на главном экране — из `mobile.ExitJSON`. Цепочка меняется со
  следующим подключением. В выгрузку всех настроек цепочка пока не попадает.
- *«Только по Wi-Fi» у резервных копий.* Служба сообщает ядру
  `ConnectivityManager.isActiveNetworkMetered` при старте и на каждую смену
  сети (`Mobile.SetMetered` → `backup.SetMetered`).
- *Обход возвращается сам.* Обход погас, потому что сервер не ответил, а
  человек его не трогал, — когда сервер вернётся, обход включится обратно
  (как круглая кнопка на ПК). Любое нажатие человека это снимает.

## Чего нельзя проверить без телефона

Всё перечисленное написано, собирается, но живьём не работало ни разу:

1. **Пометка сокетов** — существует только внутри Android.
2. **Создание интерфейса**: разрешение на VPN, уведомление, исключение
   локальных сетей из маршрутов.
3. **Отбор приложений** — списком распоряжается система.
4. **Поведение при смене сети** Wi-Fi ↔ мобильная.
5. **Откат YouTube с QUIC на TCP** — то, ради чего блокируется UDP.
6. **ТЗ 20:** соединения с дополнительными серверами и их расход батареи,
   цепочка выхода на живом телефоне, «лимитная связь» от Android, выбор папки
   для резервных копий. Список ручных проверок — в отчёте ТЗ 20.

## Как собрать APK

Локально не получится: нужны Android SDK и NDK. Сборка идёт на серверах
GitHub — там они уже установлены. Из модуля на Go делается библиотека
`core.aar`, её подключает приложение, готовый APK кладётся в файлы сборки.

Запускается сама при изменениях в `android/` или `src/`, либо вручную со
страницы Actions.

## Что делать на телефоне сейчас

Пока приложения нет, остаются готовые клиенты, которые умеют SSH и SOCKS:
**ConnectBot** (проброс порта по SSH) вместе с браузером, поддерживающим
SOCKS-прокси, или **Termux** с обычным `ssh -D 1080`. Не так удобно, но через
тот же сервер и тот же ключ.
